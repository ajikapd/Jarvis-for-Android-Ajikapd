# МАСТЕР-ПРОМПТ ДЛЯ ИИ-АГЕНТА: РАЗРАБОТКА "JARVIS" — ОФЛАЙН ГОЛОСОВОЙ АССИСТЕНТ ДЛЯ ANDROID

Ты — главный технический исполнитель (разработчик) проекта. Ниже — полный бриф. Прочитай его целиком до того, как написать первую строку кода. Действуй методично, поэтапно (см. отдельный файл ROADMAP), не перепрыгивай через этапы.

## 1. КТО ТЫ И ЧТО ТЫ СТРОИШЬ

Ты разрабатываешь Android-приложение **Jarvis** — полностью офлайн-first голосового ИИ-ассистента уровня "Джарвиса" из Iron Man. Приложение:

- поднимается голосом по вейк-ворду — русскому слову **"Джарвис"**;
- работает **полностью в фоне**: на любом экране, поверх любого приложения, при выключенном/заблокированном экране;
- упаковывается в единый **APK**;
- поддерживает **live-режим** непрерывного голосового диалога (по аналогии с Gemini Live) — пользователь может естественно говорить, ассистент отвечает, диалог не рвётся, даже если пользователь или сам ассистент переключает экраны/приложения;
- умеет **сам управлять экраном** (открывать приложения, тапать, скроллить, читать содержимое экрана) — то есть не просто выполняет команды "втёмную", а может довести пользователя или самого себя до результата навигацией по интерфейсу;
- по умолчанию работает **без интернета**, но обращается в сеть точечно — для погоды, веб-поиска, справочных вопросов ("расскажи мне про X") и подобных задач, где офлайн-данных объективно недостаточно.

Важно: это разработка **с нуля**. Не заимствуй архитектурные решения из других похожих проектов пользователя — считай, что предыдущего опыта не существует. Учись выбирать сам и обосновывай выбор.

## 2. ЖЁСТКИЕ ОГРАНИЧЕНИЯ ПРОЕКТА

1. **Бюджет — 0 (ноль)**. Любая используемая модель, библиотека, SDK, API — только бесплатные и с лицензией, допускающей некоммерческое/личное использование без ограничений по объёму запросов и без обязательной оплаты. Перед подключением любого стороннего сервиса — проверь лицензию и тарифы. Категорически нельзя: платные API по токену/запросу (OpenAI, Google Cloud Speech, Azure Cognitive Services и т.п. на платных тарифах), платные голоса TTS, платные wake-word движки (Picovoice Porcupine после бесплатного лимита персональных wake-слов — можно только если бесплатного тарифа хватает навсегда, иначе не использовать).
2. **Офлайн-first**. Ядро (пробуждение по вейк-ворду, распознавание речи, понимание команды, диалог, TTS, управление устройством и экраном) обязано работать без сети вообще. Сеть — это **дополнительный источник данных** для конкретных инструментов (см. раздел 7), а не зависимость ядра.
3. **Разработка и тестирование — на реальном устройстве**. Телефон подключён к ПК по USB с включённой отладкой (ADB). Не полагайся на эмулятор как на основной способ проверки — вейк-ворд, микрофон в фоне, экономия батареи HyperOS, Accessibility Service ведут себя специфично именно на реальном железе и именно на HyperOS. Каждый значимый этап должен быть собран (`./gradlew assembleDebug`), установлен (`adb install -r`) и вручную проверен на устройстве, прежде чем считаться завершённым.
4. **Сначала — характеристики устройства**. Прежде чем фиксировать выбор моделей (размер LLM, ASR-движок, формат квантования), обязательно собери через `adb shell` данные об устройстве:
   - `adb shell getprop ro.product.model`, `ro.build.version.release`, `ro.build.version.sdk`
   - `adb shell cat /proc/cpuinfo` (архитектура, число ядер)
   - `adb shell cat /proc/meminfo` (объём и свободная RAM — критично для размера LLM/GGUF-квантования)
   - `adb shell dumpsys package android | grep -i abi` или `adb shell getprop ro.product.cpu.abilist` (ABI: arm64-v8a и т.д.)
   - проверь наличие аппаратного ускорения инференса: NNAPI-совместимость, поддержка GPU-делегатов (через `adb shell getprop | grep -i gpu`, модель SoC)
   - объём свободного места на диске (`adb shell df /data`)

   На основе этих данных зафиксируй в отдельном файле `DEVICE_SPECS.md` конкретные цифры и из них уже выведи: какого размера LLM (в млрд параметров и квантовании) реально потянет устройство в реальном времени, какой ASR-движок по производительности подходит, стоит ли использовать NNAPI/GPU-делегаты.

## 3. ВЫБОР ЯЗЫКА И ПЛАТФОРМЫ (решение и обоснование)

Выбор оставлен на твоё усмотрение — вот обоснованное решение, которому нужно следовать:

**Основной язык — Kotlin, нативное Android-приложение (Android SDK/NDK), min SDK — ориентируйся на реальную версию HyperOS на устройстве, но не ниже Android 10 (API 29).**

Почему не Python и не гибридные фреймворки (Kivy/Chaquopy/BeeWare):
- Постоянно работающий фоновый **Foreground Service** с микрофоном, переживающий выключение экрана и агрессивный киллер задач HyperOS, — это глубокая интеграция с Android Service Lifecycle, для которой нужен нативный доступ к SDK.
- **AccessibilityService** (обязателен для управления экраном — чтения содержимого, тапов, скроллов) существует только как нативный Android API. Обёртки на Python дают в лучшем случае неполный/нестабильный доступ.
- Overlay-окно для live-режима (полупрозрачный "пузырь" поверх всех приложений, `TYPE_APPLICATION_OVERLAY`) — нативный WindowManager API.
- Локальные ML-движки для офлайн-инференса на мобильном железе (llama.cpp, sherpa-onnx, Silero) имеют официальные или community Android-биндинги через JNI/AAR — это Kotlin/Java + нативные `.so`-библиотеки, а не Python.
- Python на Android для такого проекта означал бы либо Termux (не даёт APK и полноценные фоновые системные права так, как нужно здесь), либо Chaquopy поверх той же нативной Android-оболочки — то есть Kotlin всё равно оставался бы обязательным слоем. Проще и надёжнее сразу строить всё нативно на Kotlin.

Используй Gradle (Kotlin DSL), Clean-архитектуру с чётким разделением на модули (см. раздел 5). NDK и JNI — только там, где ML-библиотека этого требует (llama.cpp, sherpa-onnx уже поставляются с готовыми `.aar`/JNI-обёртками — писать JNI-код с нуля почти не потребуется).

## 4. ТЕХНОЛОГИЧЕСКИЙ СТЕК (бесплатные офлайн-компоненты)

Подбирай точные версии моделей уже после анализа `DEVICE_SPECS.md`, но направление такое:

### 4.1 Wake Word Engine (вейк-ворд "Джарвис", офлайн, бесплатно)
- Базовый вариант: **openWakeWord** (Apache-2.0, полностью бесплатный, обучаемый) — обучи кастомную модель под слово "Джарвис" синтетическими данными (TTS-сгенерированные образцы произношения разными голосами/акцентами + аугментация шумом) в связке с ONNX Runtime для инференса на устройстве.
- Альтернатива/резерв: keyword-spotting модуль **sherpa-onnx (KWS)** — если понадобится русский датасет лучшего качества.
- Не использовать Picovoice Porcupine, если бесплатный тариф ограничен по количеству активных wake-слов на аккаунт хуже, чем нужно проекту, или требует онлайн-валидации ключа.

### 4.2 Audio / VAD
- **Silero VAD** (MIT, офлайн, лёгкая) — для определения начала/конца речи, отсечения тишины, поддержки live-режима (barge-in — пользователь может перебить ассистента).

### 4.3 ASR — распознавание русской речи офлайн
- **sherpa-onnx** с моделью **Vosk (small-ru)** или **GigaAM** (проверь актуальную лицензию — GigaAM v2 CTC был под некоммерческой лицензией; если так, для полностью свободного использования отдай приоритет Vosk small-ru или актуальной открытой модели с лицензией Apache/MIT).
- Требование: потоковое (streaming) распознавание, чтобы live-режим не имел задержек в несколько секунд.

### 4.4 TTS — синтез русской речи офлайн
- **Silero TTS** (открытая офлайн-модель, хорошее качество русских голосов, лёгкая по ресурсам) — основной кандидат.

### 4.5 Brain / LLM — понимание команд и диалог
- Локальная LLM через **llama.cpp** (Android JNI-биндинги) в формате **GGUF**, квантование **Q4_K_M** или ниже — конкретный размер модели (1–3B параметров) выбери по факту свободной RAM из `DEVICE_SPECS.md`. Кандидаты: компактные модели с хорошей русской поддержкой (например, семейства Qwen2.5-Instruct малых размеров или русскоязычные тюны на базе Mistral/Llama — выбери актуальную на момент разработки модель с открытой лицензией Apache-2.0/MIT/Llama-license, подходящую для личного офлайн-использования).
- Для простых детерминированных команд (фонарик, громкость, будильник, звонок) — не гонять всё через LLM: сначала быстрый intent-классификатор/сопоставление по правилам и локальным эмбеддингам, LLM подключай для открытого диалога, уточняющих вопросов и сложных/многошаговых команд.

### 4.6 Online-инструменты (точечно, только когда нужно)
- Погода: **Open-Meteo API** (полностью бесплатный, без ключа).
- Веб-поиск/справочные вопросы: бесплатный поисковый API без платного тарифа (проверь актуальные условия у DuckDuckGo Instant Answer API / аналогов) + **Wikipedia API** (бесплатный, без ключа) для фактических вопросов "расскажи мне про X".
- Все онлайн-инструменты — это отдельный слой "Tools", который LLM вызывает как функцию (tool calling / формализованный вызов по шаблону), а не замена офлайн-ядра.

### 4.7 Управление экраном
- **AccessibilityService** — чтение дерева экрана (для контекста "что сейчас на экране"), выполнение тапов/свайпов/скроллов/навигации "назад"/открытия приложений по intent.
- **Overlay (TYPE_APPLICATION_OVERLAY)** — плавающий индикатор live-режима, который остаётся поверх экрана при переключении между приложениями, не прерывая диалог.

## 5. АРХИТЕКТУРА ПРИЛОЖЕНИЯ (модули)

Построй проект как мультимодульный Gradle-проект с чётким разделением ответственности:

1. **core** — общие модели данных, event bus (событийная модель: `WakeWordDetected → SpeechCaptured → Transcribed → IntentResolved → ActionExecuted/ToolCalled → ResponseGenerated → Spoken`).
2. **wakeword-engine** — постоянная прослушка ключевого слова, минимальное потребление батареи в режиме ожидания.
3. **audio-engine** — захват микрофона, VAD, буферизация, эхоподавление по возможности.
4. **asr-engine** — обёртка над sherpa-onnx/Vosk, потоковая транскрипция.
5. **tts-engine** — обёртка над Silero TTS, очередь фраз, возможность прерывания на середине фразы (для barge-in).
6. **brain** — intent-детектор (быстрый путь для простых команд) + LLM-инференс (llama.cpp) для сложного диалога, разрешение неоднозначных команд через уточняющий вопрос вместо ложного срабатывания.
7. **tools** — независимые модули для каждой возможности: Flashlight, Volume/Media, Calls/SMS (если потребуется и с явным согласием пользователя на разрешения), Calendar, Alarm, WeatherTool (online), WebSearchTool (online), WikiTool (online). Каждый tool регистрируется в едином реестре с описанием, которое видит Brain.
8. **screen-control** — AccessibilityService: чтение экрана, выполнение UI-действий, распознавание "где мы сейчас находимся" (для контекста live-режима).
9. **overlay-ui** — плавающий индикатор/пузырь live-режима (визуализация "слушаю"/"думаю"/"говорю"), не блокирующий взаимодействие с остальным экраном.
10. **background-service** — Foreground Service (тип `microphone`), удержание процесса живым, обработка `BOOT_COMPLETED` для автозапуска, устойчивость к убийству процесса системой.
11. **connectivity-router** — определяет наличие сети и маршрутизирует вызов инструмента: офлайн-путь по умолчанию, онлайн-путь только для явно online-инструментов.
12. **permissions-onboarding** — экран первого запуска: последовательный запрос всех критичных разрешений и системных настроек (см. раздел 6), с понятными пользователю объяснениями зачем каждое нужно.

## 6. ЖИВОЙ РЕЖИМ (LIVE MODE) — ОБЯЗАТЕЛЬНЫЕ ТРЕБОВАНИЯ

- После активации (по вейк-ворду или вручную через overlay) устанавливается непрерывная голосовая сессия: ассистент слушает, отвечает, снова слушает — без необходимости повторного вейк-ворда на каждую реплику, пока сессия открыта.
- Поддержка **barge-in**: пользователь может перебить ассистента голосом посреди фразы — TTS должен мгновенно остановиться, ASR — начать захват новой реплики.
- Сессия **не должна прерываться** при: блокировке/разблокировке экрана, переключении между приложениями (в том числе если сам ассистент переключает экран через screen-control), сворачивании приложения. Реализуется тем, что вся логика живёт в Foreground Service, а UI (overlay) — это только тонкая визуальная прослойка поверх текущего активного приложения.
- Ассистент должен уметь и сам инициировать навигацию (открыть приложение, дойти до нужного экрана через AccessibilityService) в рамках выполнения команды, продолжая при этом диалог голосом.
- Явный тайм-аут/команда завершения сессии ("Джарвис, всё" / долгая тишина сверх настраиваемого порога) — чтобы не слушать бесконечно и экономить батарею.

## 7. ОФЛАЙН/ОНЛАЙН МАРШРУТИЗАЦИЯ

Правило по умолчанию: **всё локально**, кроме явно определённого списка online-инструментов (погода, веб-поиск, "расскажи про X" / открытые фактические вопросы, требующие актуальных данных). Brain должен:
1. Сначала попытаться разрешить команду локально (intent-правила → локальные skills → локальный LLM-диалог).
2. Если запрос явно требует online-инструмента — проверить наличие сети (`connectivity-router`); если сети нет — вежливо сообщить голосом, что нужен интернет, и не зависать в ожидании.
3. Никогда не отправлять голос/аудио целиком на сторонние серверы — ASR/TTS/LLM разговорного ядра всегда локальные; в сеть уходят только текстовые запросы к конкретному online-инструменту (например, поисковый запрос) и обратно приходит текстовый результат.

## 8. РАЗРЕШЕНИЯ И ОСОБЕННОСТИ HYPEROS (важно, иначе фон "убьют")

Xiaomi HyperOS известен агрессивным управлением фоновыми процессами. Обязательно предусмотри и явно проведи пользователя через:
- `RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW` (оверлей), Accessibility Service (включается вручную пользователем через системные настройки — приложение должно deep-link'ом привести пользователю нужный экран настроек), `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_MICROPHONE` (Android 14+), `RECEIVE_BOOT_COMPLETED`.
- Исключение из оптимизации батареи (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` + ручная инструкция для HyperOS: "Автозапуск" включить, режим экономии батареи для приложения — "Без ограничений").
- Понятный онбординг-экран, объясняющий пользователю каждый шаг простыми словами, так как без ручных действий пользователя в настройках HyperOS фоновый сервис будет убит системой в течение часов.

## 9. ПРАВИЛА РАЗРАБОТКИ ДЛЯ АГЕНТА

1. Двигайся строго по этапам из `jarvis_roadmap.md`, не смешивай этапы.
2. После каждого этапа: собери APK, установи на подключённое по USB устройство (`adb install -r`), вручную проверь заявленную в этапе функциональность на реальном железе, зафиксируй результат.
3. Веди `CHANGELOG.md` — что сделано, что проверено на устройстве, какие ограничения/баги обнаружены.

5. Код — модульный, с понятными названиями, минимум связности между модулями (общение через `core`/event bus, а не прямые ссылки друг на друга).
6. Если сомневаешься между двумя бесплатными вариантами модели/библиотеки — предпочитай вариант с более активной поддержкой сообщества и более лёгкий по ресурсам (учитывая, что устройство мобильное).
7. Не проси у пользователя денег, платных ключей или подписок ни на каком этапе — если что-то похожее понадобилось, ищи бесплатную альтернативу или переформулируй подход.

## 10. ПЕРВЫЕ ШАГИ (что сделать прямо сейчас)

1. Убедиться, что телефон виден по `adb devices` (USB-отладка включена и подтверждена на устройстве).
2. Собрать `DEVICE_SPECS.md` по чек-листу из раздела 2, пункт 4.
3. Создать пустой Android-проект (Kotlin, Gradle) со структурой модулей из раздела 5, без реальной логики — только скелет, который собирается и устанавливается.
4. Настроить `background-service` как минимальный Foreground Service, который просто живёт в фоне и показывает уведомление — проверить, что HyperOS не убивает его в течение нескольких часов реального использования телефона, прежде чем идти дальше.
5. Только после того как скелет стабильно живёт в фоне — переходить к Этапу 1 роадмапа (см. `jarvis_roadmap.md`).
