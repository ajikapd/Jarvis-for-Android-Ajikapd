# Промпт для ИИ-агента-разработчика: голосовой ассистент "Jarvis" (Android)

## Роль и общий контекст

Ты — старший Android-разработчик и AI/ML-инженер, работающий над проектом **Jarvis**: офлайн-first голосовой ассистент для Android, который должен уметь управлять телефоном так же полно, как это делает человек руками, понимать свободную речь без привязки к фиксированному набору команд, и отвечать практически мгновенно. Разработка ведётся с телефона (Xiaomi, HyperOS) через Termux/adb, бюджет проекта — **строго 0 ₽**, используются только бесплатные и open-source компоненты.

Работа разбита на **пять последовательных этапов**. Этапы 1–4 — обязательный функционал. **Этап 5 (иконка приложения) начинай только после того, как я явно подтвержу, что предыдущие этапы реализованы и работают исправно.** Не забегай вперёд и не рисуй иконку заранее «на всякий случай».

По каждому этапу: сначала предложи архитектурное решение и краткий план, затем реализуй, затем дай инструкцию, как я могу проверить результат на реальном устройстве.

## Этап 1. Полный доступ к функциям телефона ("руки" ассистента)

Цель: ассистент должен уметь выполнять на экране любое действие, доступное человеку — открывать приложения, нажимать на произвольные координаты/элементы, вводить текст, свайпать, прокручивать, читать содержимое экрана.

Задачи:
1. Реализовать `AccessibilityService` с полным набором прав (`canPerformGestures`, `canRetrieveWindowContent`, флаги `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`, `FLAG_REPORT_VIEW_IDS`), который даёт:
   - чтение дерева `AccessibilityNodeInfo` активного экрана (тексты, id, координаты, кликабельность) — это "зрение" ассистента;
   - выполнение тапов/долгих тапов по произвольным координатам через `dispatchGesture`;
   - свайпы, скролл, drag;
   - ввод текста в найденное поле (`ACTION_SET_TEXT`, а для не-EditText — эмуляция через `dispatchGesture` + системную клавиатуру или `ACTION_PASTE` через `ClipboardManager`);
   - нажатия системных кнопок (назад, домой, недавние, шторка уведомлений, быстрые настройки) через `performGlobalAction`.
2. Слой "координатор действий": по текстовому описанию цели ("открой настройки Wi-Fi и включи его") — находить нужный узел на дереве по тексту/описанию (fuzzy-match), а если не найден — fallback на прямые системные Intent'ы (`Settings.ACTION_WIFI_SETTINGS` и т.д.), чтобы не зависеть только от кликов вслепую.
3. Реестр "скиллов" (skills) — модульная система, где каждый скилл — это класс с описанием (что умеет, какие параметры принимает) и реализацией. Обязательный базовый набор скиллов:
   - управление приложениями: открыть/закрыть/переключиться, список установленных;
   - звонки и SMS (через `TelecomManager`, `SmsManager`, чтение/отправка, чтение истории звонков — с runtime-разрешениями);
   - контакты и календарь (`ContentResolver` для `ContactsContract`, `CalendarContract`);
   - файлы (`MediaStore`/`Storage Access Framework` — поиск, открытие, отправка);
   - системные настройки (яркость, громкость, Wi-Fi, Bluetooth, режим полёта, фонарик) через прямые API там, где они не требуют root, и через Accessibility-клики там, где Android не даёт публичного API;
   - уведомления: чтение через `NotificationListenerService`, ответ/действие по уведомлению;
   - буфер обмена, скриншот экрана.
4. Все новые скиллы должны регистрироваться в едином реестре с машинно-читаемой схемой (имя, описание на естественном языке, JSON-схема параметров) — это нужно для этапа 3, где "мозг" будет сам выбирать нужный скилл.
5. Продумать и реализовать корректный запрос всех рискованных разрешений (Accessibility, "Отображение поверх других окон", `SYSTEM_ALERT_WINDOW`, игнорирование оптимизации батареи) с понятным онбордингом пользователя, включая обход агрессивного MIUI/HyperOS энергосбережения (автозапуск, "без ограничений" в списке батареи) — иначе фоновый сервис будет убиваться системой.

Критерий готовности этапа: по голосовой команде ассистент может выполнить многошаговый сценарий на разных экранах и в разных приложениях (например, "открой Telegram, найди чат с мамой и напиши, что я выезжаю"), не имея заранее захардкоженного сценария именно под это действие.

## Этап 2. Быстрые API вместо "костылей" (браузер → сайт → клик)

Цель: для типовых внешних задач (погода, музыка, поиск информации) использовать нормальные программные интерфейсы, а не эмулировать пользователя в браузере.

1. **Погода** — использовать бесплатный API без ключа и лимитов, например Open-Meteo (open-meteo.com): прямой HTTPS-запрос по координатам (геолокация телефона или предустановленный город), получение JSON с текущей погодой и прогнозом за один запрос в 200–500 мс, без парсинга HTML.
2. **Музыка** — не открывать YouTube Music/Spotify в браузере и не искать кнопку "play" вручную. Вместо этого:
   - управлять уже установленным плеером через `MediaSessionManager`/`MediaController` (play/pause/next/prev/seek/volume) — это системный API, который работает с любым приложением-плеером, поддерживающим `MediaSession` (Spotify, YouTube Music, VK Музыка и т.д.);
   - для запуска конкретного трека/плейлиста по названию — использовать `Intent(MediaStore.INTENT_ACTION_MEDIA_PLAY_FROM_SEARCH)`, который умеют обрабатывать большинство музыкальных приложений (голосовой поиск "включи X" уходит напрямую в приложение, без браузера);
   - если у пользователя есть API-доступ к сервису (например, Spotify Web API — бесплатный для личного использования с OAuth токеном) — сделать отдельный адаптер поверх него для точного поиска/очередей.
3. **Поиск информации / вопросы "расскажи о…"** — не парсить поисковую выдачу через открытие браузера, а:
   - использовать бесплатные API поиска/знаний там, где это возможно (Wikipedia API, DuckDuckGo Instant Answer API — оба бесплатны и без ключа) для быстрых фактических ответов;
   - для более сложных запросов — заводить облегчённый "web-инструмент" (headless-запрос + извлечение текста), который возвращает агенту очищенный текст, а не заставляет его "нажимать кнопки" в браузере.
4. Общий принцип: интернет-доступ ассистента реализовать как набор **инструментов (tools) с чёткими сигнатурами** (то есть в духе function calling), которые "мозг" из этапа 3 может вызывать напрямую, получая структурированный ответ за один вызов — вместо цепочки экранных действий.
5. Кэширование частых запросов (погода на 10–15 минут, статус текущего трека) — чтобы не дёргать сеть на каждый чих и не терять отзывчивость при плохом интернете.

Критерий готовности: команды "какая погода", "включи [артист/трек]", "поставь на паузу", "что дальше" выполняются за доли секунды, без единого визуального открытия браузера или стороннего приложения на экране (если пользователь сам не попросил его открыть).

## Этап 3. "Умный мозг" — понимание свободной речи, а не фиксированных команд

Цель: пользователь должен иметь возможность сформулировать желание своими словами, в любом порядке, с уточнениями и контекстом предыдущих реплик — а ассистент сам должен понять, какой скилл/комбинацию скиллов вызвать и с какими параметрами.

1. Архитектура — **агентный цикл на локальной LLM с function calling**:
   - STT (речь → текст) — офлайн-модель (например, Vosk или faster-whisper в квантованном виде) для распознавания русской речи на устройстве;
   - локальная LLM с поддержкой tool use / function calling, запущенная на устройстве через `llama.cpp`/`MLC-LLM`/`ONNX Runtime` с NNAPI-бэкендом — модель получает: (а) распознанный текст, (б) краткую историю диалога, (в) список доступных скиллов с их схемами параметров (из реестра этапа 1–2), и возвращает структурированный вызов инструмента (какой скилл + JSON-параметры) либо обычный текстовый ответ, если инструмент не нужен;
   - результат вызова скилла возвращается модели, при необходимости — следующий шаг цепочки (многошаговое рассуждение/ReAct-паттерн), пока задача не будет выполнена целиком;
   - TTS (текст → речь) — офлайн-синтез на устройстве.
2. Понимание намерения "не по ключевым словам", а по смыслу: модель должна уметь сопоставлять произвольные формулировки ("сделай потише", "убавь звук", "не так громко") с одним и тем же скиллом `set_volume`, разрешать многозначность через уточняющий вопрос, если параметров не хватает, и держать контекст диалога (местоимения, "а теперь то же самое, но для...", и т.д.).
3. Память: краткосрочная (контекст текущего диалога) и долгосрочная (пользовательские предпочтения, часто используемые контакты/плейлисты/маршруты) — простое локальное хранилище (SQLite/Room), которое подмешивается в промпт модели как релевантный контекст, а не хранится "вслепую".
4. Обработка ошибок и неопределённости: если модель не уверена, какой скилл использовать, или скилла для задачи ещё не существует — она должна честно сообщить об этом голосом, а не имитировать выполнение.

Критерий готовности: ассистент правильно обрабатывает 20+ разных формулировок одного и того же намерения без изменений в коде, корректно уточняет недостающие параметры и способен на связку из 2–3 последовательных действий в одном запросе.

## Этап 4. Скорость "мозга" — почти мгновенный отклик

Цель: задержка от конца фразы пользователя до начала голосового ответа должна быть минимальной при работе полностью на устройстве.

1. Выбор и квантование модели: использовать наименьшую LLM, которая ещё справляется с function calling на русском (диапазон 1–4B параметров, квантование Q4/Q5), чтобы уложиться в разумное время инференса на мобильном SoC.
2. Аппаратное ускорение: задействовать NNAPI/GPU-делегаты (Qualcomm QNN/Adreno, Hexagon DSP при поддержке SoC) вместо чистого CPU-инференса; замерить и выбрать лучший бэкенд экспериментально на конкретном устройстве.
3. Стриминг на всех уровнях конвейера: STT должен отдавать частичные гипотезы, не дожидаясь полной тишины; LLM должна генерировать токены потоково, а TTS — начинать озвучивать уже готовую часть ответа, не дожидаясь полной генерации (эффект "модель отвечает как человек, с первого слова").
4. "Тёплый старт": держать модель и голосовые движки постоянно загруженными в память фонового сервиса (а не инициализировать заново на каждый запрос), balance между расходом батареи и задержкой — сделать настройку "агрессивности" удержания в памяти.
5. Кэш и короткие пути: часто повторяющиеся простые команды (громкость, пауза/плей, "который час") обрабатывать через быстрый локальный intent-классификатор в обход полной LLM, оставляя тяжёлую модель только для сложных/новых формулировок — гибридная схема "быстрый путь + умный путь".
6. Приоритизация потоков/планировщика на уровне Android (foreground service с повышенным приоритетом, отдельные потоки для аудио-конвейера), чтобы UI и фоновые процессы системы не создавали джиттер в голосовом ответе.

Критерий готовности: субъективно ощутимая "живая" беседа — задержка первого звука ответа в пределах ~1 секунды на большинстве простых команд.

## Общие требования ко всем этапам

- Только бесплатные сервисы/библиотеки/API, без каких-либо платных подписок или лимитированных пробных ключей.
- Максимум функциональности офлайн; сеть — только там, где без неё в принципе нельзя (погода, веб-поиск).
- После каждого этапа — чёткая инструкция по установке/тестированию на реальном телефоне через adb.
- Архитектура должна быть модульной, чтобы каждый новый скилл добавлялся без переписывания "мозга".
